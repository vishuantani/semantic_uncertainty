Six Runs to a Signal

Five faults stood between this pipeline and a semantic-entropy number worth reading. Four are fixed, one is not, and the headline result is smaller than it first looked.

Across six runs the semantic-entropy AUROC read 0.559, then 0.766, then 0.565, then 0.674, and finally 0.718 with a 95% interval of [0.614, 0.821]. Only the last of those is worth quoting, and the reason the earlier ones moved so violently is not that the method improved — it is that four separate faults were each, in turn, dominating the measurement.

Two of the faults were in decoding (sampling that never sampled; a stop condition that displaced the model's own end-of-sequence token). One was a crash (a single empty generation turning an entire run's analysis into NaN). One was the evaluation itself (unnormalised entropy measuring answer length rather than uncertainty). The fifth is still open: the correctness metric scores roughly one in five of its own positives wrong.

The honest summary is that the pipeline now measures what it claims to, and what it measures is a real but modest signal — one that does not reproduce the paper's central ordering.

02The five faults

Three were defects in code. Two were defects in how the result was being measured — which made them far harder to see.

Code · fixed Sampling that never sampled

--num_beams defaulted to 5, so the "samples" were beam-search results returning only the top beam. Repeated five times it returned the same string. 26 of 40 questions produced five identical answers.

Measurement · standing caution Entropy that measured length

Unnormalised entropy is a sum over tokens, so it tracks answer length. When wrong answers rambled, it scored 0.838 — reading "long = wrong", not uncertainty. Still correlates +0.75 with length today.

Code · fixed One empty answer, one dead run

A marker sampled as the first token halts generation at length 1; stripping the marker leaves ''. Zero tokens gives a NaN loss, and one NaN in 600 made roc_auc_score refuse the entire analysis.

Code · fixed A displaced end-of-sequence

Passing eos_token_id replaces the model's own </s> rather than extending it. The model emitted it, kept generating, and skip_special_tokens hid the seam. 19 of 600 samples were affected.

Measurement · open A correctness metric that isn't

rougeL > 0.3 on one-to-three-word answers passes on surname overlap alone. Six of the 32 "correct" answers are wrong — a 19% false-positive rate inside the positive class every AUROC is computed against.

Process · noted Runs that overwrite runs

Three runs reused one W&B name, so each destroyed its predecessor's artifacts. Two point estimates in Figure 1 can no longer be given intervals for exactly this reason.

03Why 0.766 was never real

The most instructive moment in the sequence: a result that looked like a finding, and dissolved when given more data.

Run 03 fixed the sampling collapse and semantic entropy jumped from 0.559 to 0.766. That looked like the method working. It was not.

With three correct answers out of forty, AUROC is computed over 3 × 37 = 111 pairs, so every achievable value is a multiple of 1/111 and a single question flipping moves the number by 0.009. Tripling the question count to 120 — which took the positive class from 3 to 8 — dropped the same measure to 0.565, with a bootstrap interval of [0.303, 0.816].

The lesson generalises past this run. Across the sequence, the two measures that stayed stable when the data tripled were ln_predictive_entropy (0.629 → 0.631) and number_of_semantic_sets (0.690 → 0.703). The two that swung hardest were semantic entropy (±0.20) and unnormalised entropy (±0.28). Stability under resampling was the better guide to which numbers meant anything.

The trap

An AUROC's precision is set by its smaller class, not its sample size. Run 04 had 120 questions and was still uninterpretable, because only 8 of them were correct. Adding questions to a model at 6.7% accuracy buys almost nothing; raising accuracy buys everything.

04The model was the bottleneck

Moving from opt-350m to opt-1.3b quadrupled accuracy and, for the first time, made the positive class large enough to measure against.

opt-1.3b holds the few-shot format that opt-350m could not. The question-echoing that produced answers like "In which month was the bombing of the World Trade Center?" to the question "In what month was the attack on Pearl Harbor?" disappeared entirely.

05Two bugs in the stop condition

Both live in how generation is told to stop. One crashed the pipeline outright; the other corrupted 3% of samples silently, which is worse.

Under --stop_on_turn_marker the marker ids become the stop list. Two things follow, neither intended.

First, if the model's very first token is itself a marker, generation halts immediately and the marker-stripping logic leaves an empty string. That produced one NaN in 600 samples and killed the entire stage-7 analysis. Second, and more consequentially, passing eos_token_id to generate() replaces the model's own end-of-sequence id instead of extending the list — so </s> stopped nothing:

tokens:  ' Kh'  'aled'  '</s>'  'This'  ' invention'  ' relates'  ' to' ...
decoded: ' KhaledThis invention relates to a fuel-air mixture and, more...'
         ' Khaled'   ← after --include_model_eos

The real answer was "Khaled". Everything after it is text the model had already declared finished, welded on because skip_special_tokens=True deletes the </s> from the string. This affected 19 of 600 samples, inflating their length, corrupting their likelihoods, and pushing them into their own semantic clusters — so it degraded the entropy estimates, not just the text.

06Read the normalised numbers

In the clean run the best-scoring entropy is the unnormalised one. That is the same trap as run 02, in milder form.

Answers in run 06 average 2.0 words, so the confound is far weaker than at opt-350m, where wrong answers averaged 33 words against 3.7 for right ones. But it has not vanished: correct answers remain slightly shorter (1.74 vs 2.11 words), and length still carries a weak signal about correctness (r = −0.148).

So the sensible reading of run 06 is the length-normalised pair — ln_predictive_entropy at 0.742 and semantic entropy at 0.718 — not predictive_entropy's headline 0.764. They are barely behind it anyway.

Does not reproduce

Semantic entropy is last of the entropy family here. The paper's central claim is that clustering answers by meaning beats length-normalised entropy on raw strings. In run 06 semantic entropy (0.718) sits below ln_predictive_entropy (0.742) and below the plain likelihood of the single most-likely answer (0.756). The intervals overlap heavily, so this is not a refutation — but four runs in, the ordering has not once come out in the paper's favour.

07The open fault

Every AUROC above is computed against a positive class in which roughly one answer in five is wrong.

Of run 06's 32 "correct" answers, only 17 are exact matches. The other 15 pass on rougeL > 0.3, and on one-to-three-word answers that threshold is cleared by a shared surname or a shared first word.

08Where it stands

What is settled, what is not, and what the next run should change.

  • The uncertainty machinery works

    Sampling draws genuinely distinct answers (4.38 of 5 distinct, 3.41 semantic clusters, 83% of questions multi-set). No known decoding artifact remains in run 06. The pipeline measures what it claims to.

  • The signal is real but modest

    Semantic entropy at 0.718 [0.614, 0.821] is the first estimate in the sequence whose interval excludes chance. It is not, however, the best measure available, and it does not beat the length-normalised baseline.

  • The correctness labels are still wrong 19% of the time

    Replace rougeL > 0.3 with normalised exact match plus alias matching against additional_answers. Cheapest fix, largest distortion removed.

  • Precision is still gated by the positive class

    32 positives give intervals about 0.21 wide. Roughly 50 positives are needed for ±0.10 — reachable at opt-1.3b's 26.7% accuracy with about 200 questions, and the dataset already holds them.

  • The entailment clustering deserves a look

    On at least one question DeBERTa placed five materially different answers — including an empty string — into a single semantic cluster. If that under-splitting is widespread it caps semantic entropy directly, and it is untested.
